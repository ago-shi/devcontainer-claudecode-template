ドキュメント駆動でプロジェクトを進めるための手順書。`docs/`（永続）と `.steering/`（作業単位）の
作成・更新を伴う作業のときに、この手順に従う。

**常時の原則は CLAUDE.md に従う**（1ファイルごとの承認 / `doc-reviewer` への委譲。ここには重複記載しない）。
doc-reviewer 起動時の渡し方: モードA を指定し、作成/更新ファイルと次に作るドキュメントのパスを渡す（修正はメインが行う）。

---

## A. 永続的ドキュメント（`docs/`）の内容仕様

プロジェクト全体の「**何を作るか**」「**どう作るか**」を定義する恒久ドキュメント。基本設計が変わらない限り更新しない。

- **product-requirements.md** - プロダクト要求定義書
  - プロダクトのビジョンと目的 / 対象ユーザーと課題・ニーズ / 主要な機能一覧 / 成功の定義 / ユーザーストーリー / 受け入れ条件 / 機能要件 / 非機能要件（性能・可用性・セキュリティ・運用性）
- **functional-design.md** - 機能設計書
  - システム構成図 / 機能ごとの処理フロー / データモデル・データフロー / 外部インターフェース（API・連携先） / シークレット・設定の管理方針 / ユースケース図
- **architecture.md** - 技術仕様書
  - テクノロジースタック（言語・フレームワーク・インフラ・CI/CD） / 開発ツールと手法 / 技術的制約と要件 / パフォーマンス要件
- **repository-structure.md** - リポジトリ構造定義書
  - フォルダ・ファイル構成 / ディレクトリの役割 / ファイル配置ルール
- **development-guidelines.md** - 開発ガイドライン
  - コーディング規約（使用する言語・ツールごと） / 命名規則 / シークレット管理規約 / テスト・検証規約（リント・型チェック・テストのコマンド） / Git 規約（ブランチ戦略・コミットメッセージ）
- **glossary.md** - ユビキタス言語定義
  - ドメイン用語 / 技術用語 / 英語・日本語対応表 / コード上の命名規則

## B. 作業単位ドキュメント（`.steering/[YYYYMMDD]-[開発タイトル]/`）の内容仕様

特定作業の「**今回何をするか**」を定義する一時ファイル。作業ごとに新ディレクトリを作る。

- **requirements.md** - 要求内容（変更・追加機能の説明 / ユーザーストーリー / 受け入れ条件 / 制約事項）
  - 関連する issue / PR（MR）があれば冒頭に `関連 issue: #N` を記載する（トレーサビリティ確保）。
- **design.md** - 設計（実装アプローチ / 変更コンポーネント / データ構造変更 / 影響範囲分析）
- **tasklist.md** - タスク（具体的タスク / 進捗状況 / 完了条件）。コマンド実行が要るタスクには実コマンドをコードブロックで記載する。
- **blockers.md** - ブロッカー記録（問題と原因 / 解決策 / 再発防止の教訓）
- **decisions.md** - 決定事項（決定内容と採用案 / 選択肢比較と採用理由 / 影響・注意点）

> **blockers.md / decisions.md は事前に作らない**。実装中にブロッカーが発生した時点・設計上の採用判断を行った時点で、**その都度**追記する（後でまとめて書かない。記録漏れの元）。

## C. 初回セットアップ時の手順

1. フォルダ作成: `mkdir -p docs .steering`
2. **永続的ドキュメント作成（`docs/`）**: 上記Aの 1→6 の順に作成。1ファイルごとに承認を得てから次へ。
   永続ドキュメントが無い場合はステアリング作成より先に作る。各作成後は `doc-reviewer`（モードA）でレビュー。
3. **初回実装用ステアリング作成**: `mkdir -p .steering/[YYYYMMDD]-initial-implementation` に
   requirements.md → design.md → tasklist.md を作成。各作成後は `doc-reviewer`（モードA）でレビュー。
4. 環境セットアップ
5. 実装開始（tasklist.md に基づく）。ブロッカー発生時は blockers.md、採用判断時は decisions.md へ都度記録。
6. 品質チェック（`development-guidelines.md` のテスト・検証規約に定めたコマンドを実行する）

## D. 機能追加・修正時の手順

1. **影響分析**: 永続ドキュメント（`docs/`）への影響を確認。基本設計に影響するなら `docs/` を更新。
2. **ステアリングディレクトリ作成**: `mkdir -p .steering/[YYYYMMDD]-[開発タイトル]`
3. **作業ドキュメント作成**: requirements.md → design.md → tasklist.md。1ファイルごとに承認、各作成後 `doc-reviewer`。
4. **永続的ドキュメント更新（必要時のみ）**: 基本設計に影響する場合のみ `docs/` を更新。
5. 実装開始（tasklist.md に基づく）。ブロッカー発生時は blockers.md、採用判断時は decisions.md へ都度記録。
6. 品質チェック（`development-guidelines.md` のテスト・検証規約に定めたコマンドを実行する）

### ステアリングディレクトリ命名規則

```
.steering/[YYYYMMDD]-[開発タイトル]/
```
例: `.steering/20250115-add-tag-feature/` / `.steering/20250120-fix-filter-bug/`

## E. 図表・ダイアグラムの記載ルール

### 記載場所
設計図は関連する**永続ドキュメント内に直接**記載する（独立した diagrams フォルダは作らない）。
- 処理フロー図・シーケンス図 → `functional-design.md`
- データモデル図（ER 図等） → `functional-design.md`
- ユースケース図 → `functional-design.md` または `product-requirements.md`
- システム構成図 → `functional-design.md` または `architecture.md`

### 記述形式
1. **Mermaid記法（推奨）**: Markdown に直接埋め込め、バージョン管理が容易。
2. **ASCII アート**: シンプルな図表（ディレクトリ構成・簡単な構成図等）に。
3. **画像ファイル（必要時のみ）**: 複雑な構成図等。`docs/images/` に PNG/SVG で配置。

### 更新
- 設計変更時は対応する図表も同時に更新し、図表とコードの乖離を防ぐ。
- 図表は必要最小限に留め、メンテナンスコストを抑える。
